# 智能体接入规划：Claude、DeepSeek Harness（DSH）、Hermes CLI 与 Codex

> **状态：规划草案（2026-10-13 修订），待用户批准。** 本文不改变已实现的适配器（当前仅 `mock` 与 `codex-cli`）。每个接入都须先经过 §6 的批准门槛，不得因为本文存在就开始实现或发起真实模型调用。
>
> **修订摘要（相对 2026-10-12 版）：** Claude 与 DSH 的首选传输改为 **ACP**，headless 调用保留为备选；DSH 的只读钉死改为环境变量 `DSH_PERMISSION_MODE=read-only`（替代未核实的 `--patch`）；增加 ACP 通用规则（审批自动拒绝、不声明文件系统能力、优雅取消、单飞行）与会话规则。
>
> 标注说明：**已核实** 指本机帮助、本机源码或本仓文档中可见的事实；**待验证** 指尚未在本机运行确认的行为，包括参考性结论，须本机复现后才能采用。

---

## 1. 目标与原则

1. 参与者的价值在于**不同的智能体**参与讨论（`06-第5期目标设计.md` §1）。每个接入对应一个不同的产品或运行时，而不是同一产品的多个副本。
2. 每个适配器都必须做到：服务端强制只读（或工作台授权的范围）、不使用绕过审批的开关、可取消、超时由引擎计时、输出可映射到标签字段。
3. 能力声明只写实测过的能力。未验证的能力标为 `false`，在本文中标为“待验证”。
4. 接入顺序按“结构化输出 + 可控权限 + 取消可靠 + 无需额外依赖”排列。

## 3. 统一接入模型

### 3.1 传输基座与厂商薄壳

- **`AcpTransport`（共享基座）**：负责 ACP 的 JSON-RPC over stdio、初始化、会话建立与恢复、单飞行、优雅取消与硬停止、审批请求的应答、事件归一化。基座只实现一次，厂商之间不复制传输代码。
- **厂商 profile（薄壳）**：每个厂商只声明启动命令、环境变量钉死、模型值包装、认证预检、已知行为。厂商薄壳只承载差异，单个文件预计在数百行以内。
- **headless 适配器**：不经过 ACP，独立实现（如现有 `codex-cli`），但与 ACP 适配器遵守同一份契约（`02 §1`）。

### 3.2 只读钉死方式

每个适配器必须由服务端固定以下三项，并写入任务的配置快照：权限模式、工具集或环境变量、工作目录（来自任务，见 `06 §2.1`）。

| 适配器 | 只读钉死方式 | 状态 |
|---|---|---|
| `claude-acp` | 将会话模式设为 `plan` | 待验证（映射 `plan → plan`） |
| `claude-headless` | `--permission-mode plan` + `--tools` 只读集 | 待验证 |
| `dsh-acp` | 启动环境变量 `DSH_PERMISSION_MODE=read-only` | 源码已核实；运行时待验证 |
| `dsh-headless` | 同一环境变量 `DSH_PERMISSION_MODE=read-only` | 源码已核实（快照测试使用），运行时待验证 |
| `codex-cli` | `-s read-only` | 已实现 |
| `hermes-oneshot` | 工具集限制 + `--safe-mode`；审批语义未知时不接入 | 待验证 |

**同名不同义**（DSH 文档中的说明）：DSH 的 `default` 指“工作区内放行”，`auto`/`yolo` 指“零审批”；Claude 的 `default` 指“危险操作提请审批”。因此平台只读档位必须按各厂商的原语映射，不能按字面推断。

### 3.3 输出契约映射

| 运行时 | 结构化来源 | 映射方式 | 状态 |
|---|---|---|---|
| Claude（ACP） | 会话消息；结构化约束依赖 `--json-schema`（headless） | 文本消息经解析映射为契约字段；失败时按 `06 §3.2` 保留 `raw` | ACP 下的结构化约束：待验证 |
| Claude（headless） | `--output-format json`；`--json-schema` | 直接解析 | `--json-schema` 稳定性：待验证 |
| DSH（ACP / headless） | ACP 会话更新；headless 为 `--json` 运行事件流 | 取最终消息文本，再尝试解析契约字段 | 事件结构：待验证（读取 `packages/bundle/headless/src/json-stream.ts`） |
| Hermes oneshot | `-z` 输出最终文本 | 整体作为 `raw`；结构字段靠提示词约束 | 待验证 |
| Codex | `exec --json` JSONL；`agent_message` 文本 | 同现状；结构化约束依赖 `--output-schema` | 待验证 |

### 3.4 禁止的开关与档位

以下开关与档位不得出现在任何适配器中（与 `AGENT.md` §7 一致；只读策略下另外排除非只读档位）：

| 运行时 | 禁止项 | 原因 |
|---|---|---|
| Claude | `--dangerously-skip-permissions`；`bypassPermissions`；`acceptEdits`；`auto` | 跳过权限检查，或允许编辑 |
| Hermes | `--yolo`；`--accept-hooks`；未加工具限制的 `-z` | 绕过审批；自动信任未见过的 shell hook |
| DSH | `DSH_PERMISSION_MODE=danger-full-access`；`=workspace-write`（只读策略下） | 无边界或允许写入 |
| Codex | `--dangerously-bypass-approvals-and-sandbox`；`-s workspace-write` | 同上（现状已遵守） |

### 3.5 ACP 通用规则

以下规则适用于所有 ACP 适配器（`claude-acp`、`dsh-acp`，以及未来可能加入的 `codex-acp`）：

1. **不声明客户端文件系统能力。** 初始化时只声明 `terminal: false`，不声明 `fs`。待验证：声明 `fs` 后，写入可能导致 turn 静默结束，需用替身复现（`acp-driver` 设计注释中的记录）。
2. **审批按 `optionId` 精确应答，不按 `kind` 映射。** 待验证：ACP 的 `kind` 为厂商自由命名，不宜作为判断依据（RT-PERM-1）。只读策略下，任何意外到达的 `session/request_permission` 都必须自动回答“拒绝”，并记录事件 `permission.auto_rejected`（待加入 `06 §10`）。`requiresApprovalBridge` 为 `false`。
3. **取消：先优雅、后硬停。** 先发送 `session/cancel` 通知，等待 prompt 以 `cancelled` 结束（会话保留）；宽限期后才终止进程。宽限期取值待实测，`06 §8.1` 暂定 5 秒（AI 提议）。
4. **单飞行。** 同一参与者同一时间只有一个进行中的 prompt；冲突时拒绝并发注入。
5. **认证预检。** 启动前检查必需的环境变量是否存在（只检查是否设置，不读取其值）。缺失时直接失败，并给出中文引导，不静默兜底。
6. **模型覆盖须经厂商要求的包装。**
   - DSH：待验证的模型值格式为 JSON 数组串（如 `["deepseek-official","deepseek-v4-flash"]`），裸名可能报 unknown model。
   - Claude：待验证自定义模型是否需要同时设置 `ANTHROPIC_MODEL` 环境变量并调用 `set_config_option`。

### 3.6 参与者会话（可选，默认关闭）

- 参与者可以在**同一任务内、同一参与者的相邻步骤之间**保留智能体会话（ACP 的 `sessionId`）。默认关闭，以保持“精选简报，不默认共享历史”的原则。
- 启用后，检查点只保存会话的标识，不保存会话内容（`06 §7.2`）。
- 会话绑定工作目录。工作目录变化视为新会话，不静默恢复（`06 §7.3`）。
- 是否启用，由用户决定（§8 第 7 项）。

### 3.7 依赖引入（`AGENT.md` §6 要求先说明理由）

| 依赖 | 用途 | 理由 | 替代方案 | 许可证 |
|---|---|---|---|---|
| `@zed-industries/claude-agent-acp@0.23.1`（精确钉版） | Claude 的 ACP 桥，内嵌 claude CLI | 持久会话、优雅取消、标准审批协议；不需要系统 `claude` | headless `claude -p`（取消粒度粗，无会话） | **待核对** |
| `@deepseek-ai/dsh@0.2.0-rc.1`（外部安装，不进入本仓 `package.json`） | DSH 可执行文件 | 由 `DSH_BIN` 指定路径，避免把 DSH 变成我们的依赖 | 直接使用本机源码路径（0.1.6-alpha.2） | **待核对** |
| `@agentclientprotocol/codex-acp`（可选，暂不引入） | Codex 的 ACP 版本 | 与 ACP 基座统一 | 保留 `codex exec` | **待核对** |

## 4. 各智能体的接入规划

### 4.1 Claude（建议第一个接入，ACP 首选）

**首选：ACP。** 启动方式：`node <claude-agent-acp 包的 bin 绝对路径>`，包版本精确钉为 `0.23.1`，不使用 `npx`，以保证版本可复现。

- 认证：`ANTHROPIC_API_KEY`；兼容端点时加 `ANTHROPIC_BASE_URL`。启动前预检（§3.5 第 5 条）。
- 模式：`plan`（只读规划）。
- 客户端能力：`terminal: false`，不声明 `fs`（§3.5 第 1 条）。
- 模型：本期不开放覆盖；如需覆盖，按 §3.5 第 6 条处理。

**备选：headless。** `claude -p --output-format json --permission-mode plan --permission-prompts none --tools Read,Grep,Glob --add-dir <任务工作目录> --no-session-persistence --max-budget-usd <换算上限> --json-schema <契约> --bare`，提示词经标准输入传入。

**需要验证的问题（进入实施前必须回答）：**

1. `plan` 模式（ACP 与 headless 两种）是否拒绝写入。用只读目录与替身验证。
2. 认证预检：只允许检测变量是否设置，不读取凭据文件；`~/.claude` 是否存在只作为提示，不作为依据。
3. 用量与花费：ACP 的 `usage_update` 是否带 `cost.amount` 与 `currency`，能否映射到 `usage`。
4. 取消：ACP 的 `session/cancel` 与进程树结束两种方式的实际表现（Windows 下沿用 `taskkill /T`）。
5. headless 的 `--tools` 名称与 `--bare` 对认证的影响。

**能力声明（规划）：** `transport: acp`（首选）；`supportsCancel: true`（ACP 的 `session/cancel`，待验证）；`supportsWorkingDirectory: true`；`supportsSandboxModes: false`（由 `plan` 模式代替，写明 `enforcesReadOnlyBy: permission-mode`）；`requiresApprovalBridge: false`（只读下自动拒绝）；`trustedControllerOnly: true`；`requiresWorkspace: true`；`maxConcurrency: 1`；`reportsUsage: 待验证`。

### 4.2 DSH（第二个接入，ACP 首选）

**首选：ACP。** 启动方式：`dsh acp`。待验证：shipped profile 首次使用时是否自动初始化，不需要额外配置。

- 可执行路径：构造选项 > 环境变量 `DSH_BIN` > PATH 探测。探测不到时直接失败并给出安装提示，不静默兜底。
- 只读：启动环境变量 `DSH_PERMISSION_MODE=read-only`。待验证：该值是否是唯一的权限钉死通道（握手不暴露 `mode`）；环境变量的读取位置已在本机源码中核实。
- 模型：若需覆盖，按 §3.5 第 6 条包装为 JSON 数组串。
- 版本：**钉死版本**。本机源码为 `0.1.6-alpha.2`，候选版本为 `0.2.0-rc.1`，两者差异需在 B 阶段核对。

**备选：headless。** `dsh --profile headless --json "<提示词>"`，同样设置 `DSH_PERMISSION_MODE=read-only`。这替代了原先未核实的 `--patch` 写法。本机源码快照测试已经在 headless 场景中使用该变量（`snapshots/session/headless.snapshot.ts` 第 672 行），但运行时的只读强度仍待验证。

**需要验证的问题：**

1. 环境变量钉死在 ACP 与 headless 两条路径上的只读强度（替身与只读试验）。
2. 版本差异：`0.1.6-alpha.2` 与 `0.2.0-rc.1` 在权限、审批选项 ID（待验证：`allow-once` / `reject-once`）与会话行为上是否一致。
3. `--json` 事件流中最终消息的位置、字段，以及失败与取消的事件形态（读取 `json-stream.ts`）。
4. 会话绑定工作目录：沙箱根是否等于会话 `cwd`，工作目录变化后 resume 是否失败。

**能力声明（规划）：** `transport: acp`（首选）；`supportsCancel: 待验证`；`supportsWorkingDirectory: true`；`supportsSandboxModes: true`；`enforcesReadOnlyBy: env-pin`；`requiresApprovalBridge: false`；`requiresInstalledOptionalDependencies: false`（以 `dsh` 外部安装为前提，见 §3.7）；`trustedControllerOnly: true`；`requiresWorkspace: true`；`maxConcurrency: 1`。

### 4.3 Hermes CLI（第三个接入，受限）

**为什么放在第三：** 顶层 `-z` 的审批语义未确认（待验证），不作为接入方式。在没有实测其审批语义之前，不能把它当成可以安全运行的通用智能体。目前没有现成的参考实现，接入方式需要自行调查。

**接入前置条件（全部满足才可进入实施）：**

1. 实测 `hermes chat -q "<提示词>" --oneshot -Q` 在需要审批的动作上的行为：挂起、自动批准，还是自动拒绝。这需要一次真实模型调用，**须用户批准**。
2. 若行为是自动批准，只能使用不含写入与终端工具的工具集（`-t`），并使用 `--safe-mode`、`--ignore-user-config`、`--ignore-rules` 隔离用户配置与自动注入的规则文件；否则不接入。
3. 不使用顶层 `-z`。
4. `--max-turns` 与 `--run-budget` 作为服务端的额外上限；用量记录方式待核实（`--usage-file` 的适用范围未确认）。

**拟定启动参数（规划，待验证）：**

```text
hermes chat -q "<提示词>" --oneshot -Q -t <只读工具集> --max-turns <n> --run-budget <秒> \
  --safe-mode --ignore-user-config --ignore-rules
```

**能力声明（规划）：** `transport: subprocess-stdio`；`supportsCancel: 待验证`；`supportsWorkingDirectory: 待验证`；`requiresApprovalBridge: 待验证`（若审批被跳过，则按不可接入处理）；`trustedControllerOnly: true`；`requiresWorkspace: 待验证`；`maxConcurrency: 1`。

**后续路线（不在第 5 期范围内）：** ACP（需要先安装 ACP 依赖，并确定 stdio 子进程的信任边界）与 API Server（默认关闭，启用后拥有完整工具集，按“有执行权限的宿主”对待）。

### 4.4 Codex（已接入，补齐）

- 现状保持：`codex exec --json`，`-s read-only`，不使用 shell；`requiresWorkspace` 按 `06 §2.1` 改为必填。
- 待补：`--output-schema` 的验证（进入标签化输出时）；真实端到端调用需用户批准。
- 可选：经 `codex-acp` 以 ACP 方式驱动 Codex。若 ACP 基座完成，可评估作为第二种传输方式，但不是本期必需项。`app-server` 仍不作为默认（结论不变）。

## 6. 批准门槛与验证阶段

每个适配器按以下顺序推进，**每一步都需要用户批准后才能进入下一步**（`AGENT.md` §10.1、§10.5）：

| 步骤 | 内容 | 是否调用模型 | 是否需要用户批准 |
|---|---|---|---|
| A0. 依赖与许可核对 | 核对 npm 包的许可证、版本、依赖树；记录理由（§3.7） | 否 | 随批准 |
| A. 契约与替身 | 实现 `AcpTransport` 基座；`fake-acp.mjs` 替身覆盖超时、取消、审批自动拒绝、resume 失败、空输出、畸形输出 | 否 | 随第 5 期批准 |
| B. 本机只读核实 | 版本与帮助命令；`dsh --dump-config` 等不触发模型的检查；认证环境变量是否设置（不读取值） | 否 | 否（只读检查） |
| C. 真实只读验证 | 每个适配器一次极小的只读任务，记录实际生效的只读策略、输出、用量与取消行为 | **是** | **是，逐个适配器单独批准** |
| D. 接入实现 | 适配器代码、档案注册、界面选项 | 否 | 随 C 的结果批准 |
| E. 人工验收 | 用户本人在工作台中运行一次任务并确认 | 是 | 用户本人执行 |

**关于 C 的说明**：一次真实验证即一次真实模型调用，会产生费用并发送数据。批准须限定适配器、任务内容（不含敏感信息）、预算上限与允许的工作目录。
