# 数据库与迁移

## 1. 位置与连接设置

- 默认位置与覆盖方式见 `01-环境搭建与运行.md` §5。
- 连接设置：`busy_timeout = 5000`；`foreign_keys = ON`；文件数据库使用 `journal_mode = WAL`（会产生 `-wal` 与 `-shm` 文件）。
- `node:sqlite` 为 Node 24 的实验性 API。升级 Node 时须复核行为。

## 2. 版本

| 版本 | 内容 |
|---|---|
| 1 | 第 2 期：`app_meta` 表（schema 版本与启动时间） |
| 2 | 第 3、4 期：`tasks`、`steps`、`artifacts`、`events` 表 |
| 3 | 补齐 `steps.output_body`、`steps.note`，对齐 `steps_task_ordinal`（唯一）与 `tasks_created` 索引；修复开发期 v2 草稿遗留的表结构 |

`app_meta.schema_version` 记录当前版本，`GET /api/health` 返回其值。

**计划（未实现，待第 5 期批准）**：版本 4 将新增 `messages`、`step_fields`、`checkpoints` 表，并为 `tasks`、`steps` 增加列与状态值。只追加，不删除已有列。细节见 [`03-架构设计/06-第5期目标设计.md`](../03-架构设计/06-第5期目标设计.md) §11。

## 3. 启动时的迁移流程

1. 创建 `app_meta`（若不存在）。
2. `BEGIN IMMEDIATE`。
3. 读取版本：不存在视为 0。
4. 若版本不是整数或为负，报错；若版本高于构建支持的版本，拒绝启动（不降级）。
5. 依次执行版本高于当前值的迁移。
6. 写入 `schema_version` 与 `last_started_at`，并执行读写自检。
7. `COMMIT`；任何一步失败则 `ROLLBACK` 并关闭连接。

## 4. 迁移规则

- **只追加**：迁移中不删除表或列；新建对象使用 `IF NOT EXISTS`。
- **新增版本**：在 `MIGRATIONS` 数组中追加，版本号递增。
- **已应用的迁移不得修改**；需要修正时新增迁移。迁移按版本号执行，版本号已记录后，修改 DDL 不会对既有数据库生效。
- **v3 的由来**：开发期的 v2 草稿曾在开发机上建出缺少 `steps.output_body`、`steps.note` 的表，写入步骤时报 `no column named output_body`。因此以 v3 补列修复（只追加，不删除数据）。2026-10-12 本机数据库已由服务启动时自动升级为 v3。
- **残留差异（草稿遗留，未修复）**：`steps.participant_id` 仍可空（代码始终写入，不影响运行）；`artifacts` 无指向 `steps` 的外键；`steps` 中的 `output_summary`、`error_message` 为未使用列。修复这些差异需要重建表，须经用户批准。

## 5. 备份与检查

- **备份**：停止服务后复制数据库文件，并一同复制 `-wal`、`-shm`（如存在）；或使用 SQLite 的 `VACUUM INTO` 生成一致副本。
- **检查版本**：`curl http://127.0.0.1:4317/api/health`，查看 `schemaVersion`。
- **清理数据**：本项目不提供自动清理。删除数据须经用户人工确认（`AGENT.md` §10.3）。

## 6. 注意事项

- 数据库文件与其 `-wal`、`-shm` 不入 Git（`.gitignore` 已排除 `*.sqlite*`）。
- 同一数据库文件不得被两个服务进程同时写入。
- 第 5 期的检查点依赖 SQLite 事务保证屏障一致性；若改用多进程或外部数据库，须重新评估（见 06 §7）。
